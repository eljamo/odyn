# Implementation Plans

Generated by the `improve` skill against commit `565080d` (v0.43.0), in two
passes on 2026-10-06:

- **Pass 1 — full audit.** Eight findings; the operator selected five, which
  became build plans **001–005**.
- **Pass 2 — direction audit** (`/improve next`). Six findings; the operator
  selected all six, which became design spikes **006–010**.

Execute in the order below unless the dependency notes say otherwise. Each
executor: read the plan fully before starting, honour its STOP conditions, and
update your row when done.

**001–005 are build plans**: they change code and config, and their done
criteria are `cargo test`, `make ci` and the like. **006–010 are design
spikes**: they ship no product code, their deliverable is a findings document
under `plans/spikes/`, and their strongest done criterion is that
`git diff --stat -- crates` produces no output. Do not let a spike turn into an
implementation; each one names its escape hatch.

The audit that produced 001–005 found a codebase in good shape — zero TODO
markers, 1,623 library tests, 11 trivial clippy warnings, no committed secrets,
and the security surfaces already defended and commented. What it did not find
was anything *telling* anyone when that stops being true, which is why four of
those five touch no Rust at all.

## Dependency notes

  worktrees, or expect a conflict.

## What each plan is for

### Build plans

- **001** — `crates/nebula/tests/e2e_tui.rs:37` asserts the locked-pane footer
  reads `"^q: sessions"`. The TUI stopped rendering that when the grid became
  the only view; it now reads `"^`: back to the card  …"`. One constant, two
  tests. Nothing is wrong with the product.
- **002** — `.github/workflows/` has a release builder and two Claude
  automations. Nothing runs `cargo test`, `cargo fmt` or `clippy`. The gate is
  ~60 seconds of runtime, and its absence is why 001 sat unnoticed through 35
  commits and two releases.
- **003** — `make lint` is not `-D warnings`, for the good reason the Makefile
  states: an unpinned toolchain means a new clippy lint can fail the gate with
  nobody having changed a line. A `rust-toolchain.toml` removes that reason, and
  also makes release builds reproducible — today they use whatever stable the
  runner image shipped.
- **004** — `release.yml` publishes four `.tar.gz` binaries with no checksum,
  and `install.sh:48-51` installs one without checking it. The adjacent risks
  were already handled (`upgrade.rs:242-244` stages the installer rather than
  piping it to `sh`, into the 0700 runtime dir); this is the one hop with
  nothing verifying it.
- **005** — 287 locked packages including `axum`, `rusqlite`, `portable-pty`
  and `nix`, and nothing checks them against RustSec. No Dependabot either.
  Separately, the patched `vendor/vt100` is a path dependency pinned at 0.16.2,
  which no tool can watch — so it gets a human pointer instead.

### Spikes

- **006** — `crates/nebula-tui/src/lib.rs:64-116` exposes seven one-shot
  commands for an agent to drive nebula from inside its own session. Not one is
  a query. `nebula spawn`'s own output tells the model its sibling *"shows in
  the sessions list"* (`ipc.rs:352-354`) — a list no command can read. The
  sibling's id is already on the wire (`protocol.rs:468-471`) and discarded by
  `ipc.rs:260`'s `..`. Four separable questions, including whether `nebula wait`
  should exist at all. Rolls in the small one: `nebula spawn --kind` cannot name
  a custom harness, and `cli.rs:56-58` says so in its own doc comment.
- **007** — Five of seven built-in harnesses report status. Muse and grok set no
  hook dialect, and three separate places in the code say so with the word
  *until* (`entities.rs:59-65`, `registry.rs:2474-2478`). So: no needs-feedback
  dot, no auto-title, no issue/PR context rule — and for muse, no resume either,
  plus an Effort row `harness.rs:112-114` calls *"a reserved row (stored, never
  sent)"*. The spike finds out what those CLIs actually expose before anyone
  sets a field, because an unverified dialect ships *wrong* status.
- **008** — Nine `gh` verbs across the TUI and no `create`, anywhere. Meanwhile
  `.claude/skills/pr-description/SKILL.md:174-175` runs `gh pr create
  --body-file` off ten templates, so the loop is: work in nebula → leave nebula
  → run a skill. Weighs four shapes including *nothing*, and answers the two
  prerequisites: nebula tracks no upstream state, and who should write the body.
- **009** — The DONE SOUND, FEEDBACK SOUND and desktop notification all live in
  `crates/nebula-tui/src/event_loop/alerts.rs`, driven from the TUI's frame loop
  at `event_loop.rs:743-762`. There is no notification path in `nebula-daemon`
  at all — yet the daemon owns the status edge (`registry.rs:309`) and outlives
  every client by design. Mostly a policy question: what may a daemon do
  unattended. WORKTREE HOOKS (`worktree_hooks.rs:1-22`) are the precedent that
  answers most of it.
- **010** — A project's settings are two shell lines (`config.rs:1354-1379`).
  Everything shaping how agents run is one global value for every repo —
  `worktree_base_branch` most sharply, read at `registry.rs:859` for every new
  worktree. The mechanism for a per-project row already exists and is complete.
  Keeps "per-project" and "committable" apart, because `.nebula.json` runs into
  the reason it is safe at all (`ARCHITECTURE.md:81`).

## Findings considered and rejected

Recorded so nobody re-audits them.

- **The 123 prod `unwrap`/`expect` calls.** Almost all are
  `Mutex::lock().unwrap()`, the standard Rust idiom for "a previous panic
  poisoned this". Not worth doing.
- **`git()` in `crates/nebula-daemon/src/git.rs:34` has no timeout** where its
  remote-operation siblings do (`git.rs:283`, `:362`). A local `git` command
  hanging is rare enough that the added machinery costs more than it saves.
- **Blocking `std::fs` calls inside `async fn`s** at `git.rs:139` and `:256`.
  Microseconds on a background poll tick. Not worth doing.
- **The 11 clippy warnings as a standalone cleanup.** They are real but
  trivial; clearing them only matters as the prerequisite to a strict gate,
  which is why they live inside plan 003 rather than in a plan of their own.
- **`ui.rs` has the thinnest test ratio in the repo** (4,789 prod lines, 369
  test). It is the render layer, covered in practice by `make shot` and the
  `e2e_tui` snapshots. Manufacturing unit tests for render functions would add
  maintenance without adding confidence.
- **Cloud sessions for harnesses other than Claude.** `claude --cloud=<task>`
  and its scanner (`crates/nebula-daemon/src/pty/cloud.rs`) are Claude-specific
  because only Claude ships a cloud product. Not an asymmetry nebula can close.
- **Everything security-shaped that was checked and found sound**, so it is
  not re-examined next time: shell quoting in `ssh.rs` and `tunnel.rs` (every
  user value passes through `nebula_core::shell::single_quote`, with tests for
  the embedded-quote case); the hook receiver's bearer token (constant-time via
  `subtle`, bound to `127.0.0.1:0`); the in-place-restart trust boundary
  (requests arrive through the 0700 runtime dir, and the target binary is
  version-probed before `exec`); all SQL in `store.rs` (bound parameters, column
  lists from constants); the `ps` subtree walk in `metrics.rs` (cycle-guarded
  and tested); byte-index string slicing in `branch_name.rs` and
  `dropped_files.rs` (ASCII-only and `char_indices` respectively). No committed
  secrets, no `.env`, no PII in logs.

## Findings surfaced but not planned

From pass 1, three findings the operator did not select. Recorded with their
evidence so they are not lost.

- **`crates/nebula-tui/src/app.rs` is the TUI's junk drawer.** 5,667 prod
  lines; `struct App` spans `app.rs:3192-3869` with roughly 157 fields; 262
  methods; about 20 unrelated view structs in one file (`ContextMenu:424`,
  `PromptDialog:843`, `DiffView:1018`, `FileFinder:1503`, `GrepView:1597`,
  `HostsView:1739`, `SettingsView:1794`, `MetricsView:1860`). 98 commits in
  three months. Extracting the self-contained view structs is mechanical and
  low-risk; grouping `App`'s fields is a separate, harder job.
- **`crates/nebula-tui/src/event_loop.rs` is 32,084 lines** (11,086 of them
  prod) and the highest-churn file in the repository at 124 commits in three
  months. `event_loop/launcher.rs` is a second 11,732-line file. The seam is
  already cut — `event_loop/` holds ten submodules between 133 and 2,247
  lines — and an obvious first slice exists: the pull-request orchestration
  cluster at `event_loop.rs:970-2038`, about 1,070 lines from
  `lookup_pull_request` to `refetch_pr_detail`, with its own channels and land
  functions.
- **`ARCHITECTURE.md:32` contradicts the code.** It states "the grid draws no
  link rows", but `App::links_in` (`app.rs:4952-4980`) pushes a
  `LinkRow::Saved` for every stored link, and `event_loop.rs:5079-5082` still
  offers "Edit URL" and a confirmed delete on those rows. The paragraph is
  right that nothing creates links any more and wrong about the TUI. It matters
  more than a usual doc nit because `ARCHITECTURE.md` is the brief every agent
  working here reads — one that trusted the sentence would delete reachable
  code.

From pass 2, direction items that are real but deliberately outside the five
spikes:

- **Finish retiring the `links` entity, or give it a create path.** Roughly 170
  prod lines across all four crates — the `Link` entity and `LinkId`, the
  `links` table from migration 16 (carried through migration 28), six store
  methods at `store.rs:841-899`, `UpdateLink`/`DeleteLink` in
  `protocol.rs:289-296` → `server.rs:567-570` → `registry.rs:2235-2245`, and
  the TUI's `LinkRow`, menu actions and edit prompt. Keeping the stored rows is
  a documented decision (`ARCHITECTURE.md:32`) and settled; the half-built UI
  surface around them is not. Pairs with the doc-drift item above.
- **`gh issue create` is the cheaper sibling of spike 008** and was excluded
  from it on purpose: an issue needs no branch, no push and no write access to
  code, so its answer may well be yes where the pull-request answer is no. The
  issues modal already runs `list`, `view`, `comment` and `edit`
  (`issues.rs:451`, `:500`, `:550`). Deserves its own small spike.
- **Knowing whether a worktree's branch is ahead of its remote** is useful on
  the grid independently of pull requests — it is the thing that tells you a
  session's work exists only on your disk. nebula tracks no upstream state at
  `565080d` (no `@{u}`, no `rev-list --count`, no `--ahead-behind` anywhere).
  Spike 008 prices it as a prerequisite; it stands alone as a finding.
- **Two doc comments look stale about custom harnesses.**
  `crates/nebula-core/src/entities.rs:72-75` says they have *"process-based
  status and no resume"*, but `CustomHarness` has a `hooks` field
  (`harness.rs:780-785`) and `hook_dialect()` accepts five dialects
  (`harness.rs:276-285`). That same doc at `:781-782` lists only four. Spike 007
  investigates and records; neither should be edited as a drive-by.

patch itself.

`cargo audit` could not be run (not installed), so **this batch contains no
dependency-advisory data**. Plan 005 step 1 establishes it, and that is the
first thing its executor reports.

**Pass 2 (direction only).** No correctness, security, performance or test work;
the pass-1 findings stand unchanged. `harness.rs`, `worktree_hooks.rs`,
`pty/progress.rs`, `pty/cloud.rs` and `claude_bg.rs` were read in this pass and
are no longer in the un-read list above.

**The open GitHub issues were not read.** `gh` was not on the auditing shell's
`PATH`, and the repository's open issues are normally the strongest direction
signal there is — stated-but-undelivered intent, straight from users and from
the maintainer. Everything in pass 2 is grounded in code, docs and
`.claude/skills/` instead. A future `/improve next` run with `gh` available
should start there, and may well reorder these five.
